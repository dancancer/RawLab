## Actual Stage3 Regression

Three new fixtures are generated by `lutools/tests/make_jxl_fixture.py`:

- `linear-jxl-stage3-lens.dng`: a lossless 32-by-24 LinearRaw ramp, synthetic
  camera/lens/focal EXIF and a required OpcodeList3 WarpRectilinear operation.
  The serialized payload follows the pinned SDK implementation: one shared
  plane, radial coefficients 1/-0.08/0/0, zero tangential terms, center 0.5/0.5.
- `linear-jxl-lens.dng` and `linear-lens.dng`: the same unwarped samples and
  synthetic metadata, JXL and uncompressed respectively, matching `lenses.xml`.

This runs the actual SDK through LibRaw, not a manually supplied
`embeddedGeometry` Boolean. The native test checks actual warped pixels,
Lens-off/on identity and no applied Lens flags after Stage3, WB reload and
camera-WB restoration, then actual distortion/TCA on the next no-Stage3 JXL and
ordinary DNG. A C session repeats Stage3 -> JXL -> plain -> Stage3 and checks its
post-render report for every input.

RED: after the Stage3 fixture, the no-Stage3 JXL incorrectly retained report
state 8 instead of applying Lens correction. See `lens-integration-macos-final.log`.
LibRaw `recycle()` zeroes image metadata but not `process_warnings`; resetting
only the wrapper Boolean was insufficient. `openAndUnpack` now clears only
`LIBRAW_WARN_DNG_STAGE3_APPLIED` before each open/unpack. Other warnings, SDK
flags, decode error handling, exposure and WB processing are unchanged.

GREEN on macOS, iOS, Android and Windows: SDK geometry changes unwarped pixels
by a maximum of `0.0320438` in the checked linear red channel; additional Lens
correction leaves the Stage3 result exactly unchanged. No-Stage3 JXL/plain
reuse applies both distortion and TCA, with matching pixels. C ABI reports stay
input-specific and SDK OOM retains its expected status.

The existing 14 synthetic DNGs byte-match regenerated output; only the three
new synthetic files were added. Windows transfer explicitly allowlists these
files; arbitrary/private RAWs remain excluded. Mobile native-test scripts also
copy the test database. Production Android assets do not include these fixtures.

## Dependency and Packaging Regressions

An initial Mac dependency attempt loaded an older LibRaw from a different
prefix alongside a newer SDK, producing an OOM-category failure. Dynamic-library
references and cached pkg-config directories proved the mismatch. The final
checks use a consistent worktree-owned LibRaw/SDK build and fresh core configure;
unchanged OpenCV/wavelib source-build dependencies may be reused. No other
worktree's binaries or configuration were modified.

Mac native Swift tests first failed to link `dng_host`. Their existing Lensfun
link parameters now also include `rawlab-dng-sdk`; the focused settings/render
and batch checks pass. These mechanical lines overlap the rendered-DNG feature's
SDK-link additions and must be reconciled with its later target merge.

The final boundary review found one additional link command in
`master-recipe-render.sh` missing both Lensfun and the SDK. Running the unchanged
script reproduced unresolved `dng_host` and Lensfun symbols (exit 1); adding
only the two pkg-config packages fixes the link. The complete 14-recipe gate
then passed on real DJI DNG and Sony ARW fixtures, including 0/50/100/200 percent
strength, forced Metal parity, frozen JPEG/PNG batch output and unchanged RAWs.
An intervening attempt used a minimal decoder-only synthetic JXL fixture, which
ImageIO cannot read for the metadata-export portion of this real-RAW harness;
it stopped with `ExportMetadata.Failure.unreadableSource` (exit 133). The final
run uses the intended real fixtures without changing or weakening assertions.

The reused iOS framework output initially contained 112 XML files because
directory copying nested `version_1` inside an existing `Lensfun` resource.
The flat-snapshot verifier fails on that state. The builder now refreshes only
its generated Lensfun resource and copies directory contents; final slices
contain 56 XML files, both dependency license groups and no extra runtime dylibs.
Previous XCFramework artifacts are retained by the existing packaging script.

After the code gates above, the docs-only target
`261b9323bea13f562bcfee7db736fcf1728704f5` was normally merged. Its 126 changed

The preceding source parent is `0316579`, including the separately verified
master-recipe link fix above.

The 27 textual conflicts consist of 20 existing Swift link commands, the common
native environment, Mac build/notices, shared CMake, iOS resources/licenses,
Android batch tests and the Windows test entry point. Resolution combines SDK,
Lensfun and TIFF links/notices. The Lens-only and newly introduced rendered-DNG
Swift scripts also receive the complete dependency union. Both Android test

The DNG writer, its pinned TIFF dependency and SDK/LibRaw glue are byte-identical

The already-reviewed target's non-overlapping implementation and prior platform
evidence are reused rather than independently re-audited.

The new `rendered_dng_tests.cpp` combination case loads real Stage3/no-Stage3 JXL
fixtures, enables both Lens corrections and writes FINAL DNG through the C API.
Independent libtiff float scanlines, sRGB-encoded, match the reference RGB8 buffer;
observed Mac maximum errors are `0.499693` and `0.499634` RGB8 steps. Post-file
reports correctly distinguish embedded geometry from actual distortion/TCA.
This case is compiled only when both SDK and Lensfun are enabled.

Both original reviewers found a new iOS wrapper integration defect: the RAW and
buffer `exportDNG` entries created a session without loading the bundled Lensfun
database. Two calls to `loadLensDatabase`, before recipe/session configuration,
are the complete production fix. The focused `lens-dng-export.sh` harness uses
the packaged framework resource, a default processor, real RAW geometry,
CPU/forced Metal, explicit native-file references and frozen settings.

RED: both entries ignored an explicit invalid database (`RAW=false,
buffer=false`, exit 133). GREEN: both reject it with the expected database error;
Lens-enabled DNG differs from off, equals an explicitly configured native export
on each backend and preserves frozen settings and the original RAW. The initial
simulator run exposed only the buffer failure because host system-db fallback
could mask the RAW omission. The explicit-invalid-db assertions prevent that
false green without altering system files or weakening pixel assertions.

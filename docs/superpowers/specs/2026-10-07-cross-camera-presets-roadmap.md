# RawLab 跨相机色彩预设整体规划

状态：2026-10-07 用户已批准执行。首先落实 P0/P1/P2 的首个里程碑；各阶段按下列证据门禁推进，不自动提交或发布。

执行进展：批量诊断、只读 native 校验、Mac/Android 托管外观库、固定样本工具及首批运行回归已落实。来源软件参考和受控同场景 RAW 尚缺，显示域 LUT 烘焙未通过原误差门禁；完整质量里程碑仍未完成。实际证据与未完成项见 [验证记录](../../verification-cross-camera-presets-2026-10-07.md)。

基线：2026-10-07，源码 `81f98c350b8f76434dcdbaa21331485a1f382651`。

## 目标与成功标准

把已有厂商 LUT、创意外观、DCP 和可解释的 XMP 色彩配置，适配为能用于其他相机 RAW 的外观。保留目标相机自己的校准、白平衡和基础显影，不把源相机校准直接套在目标传感器数据上。

产品目标是：用户导入已有预设，看到兼容情况和必要条件，选择自己的 RAW，预览并导出；导入的外观在重启后仍可使用。

`for any camera` 的可交付定义是：同一份已适配外观可以用于 RawLab 支持解码的不同相机 RAW；实际验证过的机型、光源和场景单独列出。可解码、可运行、风格迁移经过验证是三个不同结论。

不承诺从未知文件或固件中自动恢复所有厂商算法，也不把 Adobe Camera Matching 等同于原厂机内 JPEG。缺少源文件、输入约定或处理阶段时，明确说明缺什么，不用近似结果冒充完整支持。

### 验证对象

- 原厂公开 LUT：首先验证其声明的输入输出约定和表计算，再验证跨相机基础输入。
- Adobe Camera Matching DCP：首先以该 DCP 和明确的来源软件渲染为参考，不直接宣称复刻了同名机内外观。
- XMP：验证完整的受支持执行链，包括基础 profile、表、amount 和依赖；只读取到 XML 不算支持。
- 只有相机 JPEG 或配方说明的风格：属于另一个需要样本拟合的任务，本路线不把它混入文件适配。

## 当前起点

| 项目 | 已有能力 | 尚缺能力 |
| --- | --- | --- |
| RAW 基础处理 | LibRaw 解码、目标相机矩阵、相机空间白平衡、明确的曝光基准 | 多品牌同场景的输入一致性证据 |
| 通用 LUT | OCIO 读取，显式合同，离线转为兼容 CUBE，采样误差检查 | 常见来源适配配置和非专业用户入口 |
| DCP | D65 外观适配，HSM/LookTable/tone/EV，原生 `.rlook` CPU/Metal | 部分缺失曲线和黑位语义、多光源及其他阶段的支持决策 |
| 本地资源 | 484 份松下/理光 DCP，78 份相关及共享 XMP | 资源清单到可用外观库的转换 |
| 客户端 | Mac/Windows 源码支持导入准备好的 `.cube/.rlook` | 持久化外观库、移动端导入、源预设制备入口 |
| 验证 | 数学阶段、CPU/GPU、预览/导出回归 | 独立参考渲染及受控跨相机验证 |

本地 484 份 DCP 中，388 份在默认参数下通过现有读取器，96 份缺少 ToneCurve。这个比例仅描述读取覆盖，不代表编译覆盖或视觉质量。78 份 XMP 当前没有执行链。

## 技术路线选择

| 路线 | 收益 | 代价 | 选择 |
| --- | --- | --- | --- |
| 全部转换成 RGB CUBE | 客户端简单，沿用现有 GPU | 复杂变换存在烘焙误差，空间/自适应操作不能靠普通 CUBE 表示 | 只用于通过误差门禁的静态变换 |
| 桌面制备加现有原生运行时 | 保留 CUBE 与 `.rlook` 两条成熟路径，移动端不引入 Python/OCIO | 制备和使用分两步，需要补产品入口 | 推荐 |
| 完整厂商或 Adobe 显影引擎 | 理论覆盖更多来源语义 | 范围过大，许多依赖和算法尚不明确 | 不作为当前目标 |

采用第二条路线。复用现有模块，不先重做渲染器，不建立通用节点引擎，不为尚未验证的格式预先设计新容器。

### 数据流

```text
用户已有源预设
  -> 识别格式和依赖
  -> 确定输入输出约定与显式近似策略
  -> 适配、编译和误差检查
  -> 已有 .cube 或 .rlook 成品及其元数据
  -> 各端持久化外观库

目标相机 RAW
  -> 目标相机自己的解码、校准、白平衡和曝光基准
  -> 共同线性 RGB
  -> 成品外观执行
  -> 现有强度、调整、预览与导出
```

不要求所有预设都先变成 F-Log2 CUBE。DCP 继续使用原生阶段，通用静态 LUT 沿用现有制备路径。共享线性 RGB 是工作约定，不是所有相机已经完成色彩标定的证明。

### 模块职责

| 模块 | 职责 | 现有落点 |
| --- | --- | --- |
| 来源适配 | 识别、依赖检查、合同、显式策略、制备诊断 | `lutools/lutprep/` |
| 原生执行 | 严格校验成品、执行已支持阶段、报告实际后端 | `lutools/src/core/`、`lutools/src/ffi/`、`lutools/src/gpu/` |
| 外观库 | 托管导入文件、稳定 ID、元数据、重启恢复和删除 | 各客户端现有存储与外观选择路径 |
| 质量验证 | 固定样本、参考渲染、数值检查、范围明确的质量报告 | `lutools/tests/` 和独立验证工具 |

优先保留 PHOTO v2 请求布局。客户端需要统一的成品检查或元数据读取时，复用核心校验，必要时增加只读接口，避免四端各写一套文件解析器。

## 阶段路线

### P0 资源盘点与质量基准

目的：先知道哪些文件值得支持，以及什么结果算对。

交付物：

- [x] 将来源格式、依赖、缺失条件、实际读取/编译结果分开记录，给出可复现的批量诊断。
- [x] 首批候选固定为 Sony FL、Ricoh GR III Positive Film、Panasonic DC-S5 Vivid，以及各一份合同已知的显示域和 Log 域 LUT；执行前核对本地源文件并固定版本。
- [x] 建立合成色块、灰阶、肤色/天空/植被/高饱和色/高光的固定测试集。
- [ ] 为代表预设导出来源软件参考，记录软件版本、基础 profile、曝光、白平衡、amount、自动处理和输出色彩空间。
- [x] 将现有 Sony/DJI 素材纳入运行回归；另列受控跨相机拍摄所需素材，随机不同场景的 RAW 不充当同场景校准证据。
- [ ] 固定各验证项的指标、阈值和适用范围，之后修改适配算法时不得按结果临时放宽。

验收：每份样本都有明确状态和原因；读取成功不会被报告为效果通过；缺少参考的项目显示“效果未验证”。

建议实施落点：扩展 `lutools/lutprep/__main__.py` 的只读诊断；新增批量盘点和参考比较工具；在 `lutools/tests/` 使用可公开的合成 fixtures，真实预设和参考图仍放本地忽略目录。

### P1 首批可信的跨相机外观

目的：用现有支持范围完成一个可重复验证的纵向流程，不先追文件数量。

交付物：

- [x] 对 P0 的代表 DCP 使用现有 `.rlook` 路径，验证 source stages、CPU 参考、实际 GPU 和最终导出。这里只确认运行和内部数值回归，来源软件效果仍未验证。
- [ ] 对代表通用 LUT 提供经过核实的输入输出合同；保留无合同拒绝和采样误差门禁。
- [ ] 检查同一预设在现有不同目标 RAW 上的曝光、白平衡、灰阶和典型颜色，分别定位基础显影差异与外观差异。
- [x] 只修复被参考和回归证明的偏差；没有证据时不统一修改相机矩阵、默认 `+0.7 EV` 或 D65 适配策略。本轮未修改渲染数学或 shader。
- [x] 为每个成品记录来源、制备器版本、使用策略、误差及已验证范围。

验收：至少打通一份 DCP 和一份通用 LUT，从原文件到两种目标 RAW 的预览、导出和可重复报告。两种目标 RAW 的运行通过不能代替受控同场景质量验证，后者是否具备要单列。

建议实施落点：`dcp.py`、`native.py`、`pipeline.py`、`bake.py`；只有证据指向原生阶段时才修改 `dcp_look.cpp` 或 shader。继续使用现有 RAW 和加速回归。

### P2 Mac 与 Android 完整使用流程

目的：把已经能算的能力变成用户能持续使用的产品。

第一批只导入准备好的 `.cube/.rlook`，不以源 DCP/XMP 一键转换作为手机入口的前置。

- [x] Mac 和 Android 导入成品时，先复制到临时位置并调用统一校验，再原子安装到应用持久化目录。文件与索引分别原子安装，常规异常回滚已测；导入时进程强杀仍可能留下未注册的托管文件，不承诺跨文件事务。
- [x] 采用应用托管副本，不依赖外部原文件路径长期有效；Android 使用 `filesDir` 而非当前会清理的 RAW 临时缓存目录，Mac 使用 Application Support。
- [x] 外观记录包含稳定 ID、显示名、成品相对路径、格式/版本、可用的来源与策略信息；缺少历史元数据的兼容 CUBE 可以保留，但不虚构来源或质量认证。完整制备策略仍保存在原样复制的成品元数据中。
- [x] 支持选择、重命名、删除和重启恢复；同名文件不能静默覆盖。删除仅移除应用托管副本，不删除用户源文件。
- [ ] 区分内置与用户外观；将不支持、需补充信息和显式近似的原因显示给用户，不把底层错误统一变成“文件损坏”。
- [ ] 检查导入取消、校验失败、文件缺失、进程重启、大文件及低存储空间时的库状态一致性。

验收：桌面制备一份外观，传给 Android 后导入、应用于 RAW、导出、重启再用；用户删除原传输文件不影响已导入外观。手机不安装 Python 或 OCIO。

建议实施落点：Mac `EditorModel.swift` / `FilmDock.swift`；Android `EditSettings.kt` / `PhotoStorage.kt` / `MainActivity.kt` / `EditorScreen.kt`；在各端增加职责单一的外观存储实现和测试。完整照片编辑 sidecar、批量编辑和云同步不在这一阶段。

P2 可以在 P0 固定成品诊断约定后与 P1 并行，不必等待所有预设都完成视觉验证。界面必须保留“运行支持”和“效果验证”之间的区别。

### P3 按真实需求扩大预设覆盖

分成独立子项目，每个子项目都允许单独交付或停止，不能为了一个“支持 XMP”开关静默丢掉字段。

| 子项目 | 首批范围 | 推进条件 | 暂不处理 |
| --- | --- | --- | --- |
| DCP 缺失曲线和黑位策略 | 本地 96 份被缺失 ToneCurve 阻挡的资源 | 选择有依据的明确曲线/黑位策略，并完成来源参考对照；近似策略单独标记 | 自动把缺失曲线当 identity，或将省略黑位标为完整 Adobe 兼容 |
| 静态 XMP 外观 | 先调查 Artistic 中仅包含静态 Look/RGB 表的 8 个候选 | 明确表编码、应用顺序、输入约定和默认 amount，直接评估与烘焙误差都通过 | 因 XML 可读就宣称可执行 |
| 带基础 profile 的 XMP | Panasonic camera profiles、Adobe Raw | 解析并验证基础 DCP 与 XMP 的依赖顺序，防止重复曲线/曝光；明确跨相机如何使用源机型限制 | 只删除 CameraModelRestriction 后直接套用 |
| 显影配方与自适应配置 | 单独调查有明确需求的条目 | 每个操作都有可验证的语义和实现成本 | 将 Clarity/Shadows 等字段粗略映射为现有同名或近义滑块 |

静态 XMP 的可行性调查先完成一份 Artistic 代表，验证失败就记录阻塞，不把“8 个候选”变成必须兼容的承诺。即使没有机型限制，仍需确认它要求的基础显影和运行环境。

在误差门禁允许时，静态 XMP 离线编译为现有 CUBE。不要把 XMP RGB 表硬塞进 DCP 专用 `.rlook` v2。只有高价值、定义清楚的阶段无法在既定误差内展平时，才单独评估格式扩展，并要求 CPU 参考、旧版兼容、拒绝规则与后端测试。

多光源 DCP 是测量驱动的后续选项：先固定现有 D65 模型作为基线，再用受控样本验证候选方案确有改善，且没有对已经白平衡的目标数据二次校正。不得把“标签更多”直接当作效果更准确。

建议实施落点：为 XMP 建立独立的解析和适配模块，复用现有 contract、baking 和 diagnostics；DCP 策略留在 DCP 模块。P3 的各子项目实施前各写一份范围明确的设计和实施计划。

### P4 扩大相机与平台验证范围

- [ ] 按 RAW 处理差异选择样本，不按品牌数量凑覆盖：现有 Sony/DJI 后，增加实际可获取的 Canon、Nikon、Panasonic/Ricoh、Fuji X-Trans 等代表。
- [ ] 为同场景拍摄建立日光、暖光、LED 三类可重复条件，包含中性和典型饱和色；记录灰卡、曝光与白平衡归一化方法。
- [ ] 对发现的输入差异进行归因；需要机型或光源修正时，作为目标 RAW 输入处理的一部分，不复制到每个外观中。
- [ ] Windows/iOS 复用已经稳定的成品与外观库约定，完成导入、持久化、预览和导出；在真实平台重新构建和验证，不能用 Mac 的测试代替。
- [ ] 根据实际延迟决定是否增加 GLES/D3D11 原生 DCP 加速；保留 CPU 参考及 Auto 回退，Force 不伪装成功。

验收：发布支持矩阵，分别列出可解码、外观可运行、同场景效果经过验证、平台运行测试的范围。每新增一类目标 RAW 或一个后端，都有对应的独立样本与回归，不做“全部机型已校准”的推断。

## 质量门禁

### 数学和工程正确性

- 保持现有 CPU/Python 同输入 `2e-6` 误差门槛及现有 CPU/GPU 8-bit 输出 2 DN 门槛；新算法若需要不同域或指标，单独解释并设独立测试，不能放宽原回归掩盖问题。
- 通用烘焙保留现有默认 `max_error=0.02`，明确它是采样通道误差，不是视觉色差或数学全局界；超标不能进入正常支持列表，显式近似另行标记。
- 原始 RAW、源预设和来源参考只读；失败导入不改变现有库，失败转换不覆盖成品。
- 预览、最终渲染和导出保持同一语义；实际 GPU 后端和 CPU 回退如实报告。

### 风格与跨相机质量

P0 在固定参考下记录灰阶/曝光偏差、选定色块的色差与色相、高光裁剪比例，以及可重复的视觉并排检查。来源软件效果对照和目标相机基础输入对照分别出报告，不能用一个平均分掩盖两类问题。

视觉阈值根据参考渲染的重复性和受控素材确定，在适配代码修改前冻结。整体规划不预设一个适用于所有风格的 Delta E 数字；强风格本身可以偏离真实色彩，比较对象必须是该风格的明确参考。

没有参考的条目可以标为可运行/实验性，但不能标为忠实度已验证；参考来自 SDK、Lightroom 或相机 JPEG 时分别注明，不能混用。

### 使用与平台质量

- Mac/Android 首批必须覆盖导入、实际 RAW 渲染、导出、进程重启、源文件失效和删除；界面变化实施时使用现有设计规范并检查手机/平板、深色和大字体。
- Windows/iOS 的发布必须有本平台当前源码构建和运行证据；旧二进制不因共享源码更新自动获得新能力。
- 现有 CTest、Python、客户端测试按改动范围运行。涉及共享渲染时增加真实 RAW、CPU/GPU 和最终导出回归。

## 首个交付里程碑

建议以 P0、P1 和 P2 的有界范围形成首个里程碑，不等 78 份 XMP 全部处理完：

1. 用户从自己的资源中制备首批代表 DCP 和合同已知的通用 LUT。
2. 每份成品带有可检查的适配策略、兼容诊断和验证范围。
3. 在 Mac 和 Android 导入、应用到不同品牌 RAW、导出并在重启后复用。
4. 至少一个代表风格有明确的来源参考对照；跨相机受控验证是否具备单列。
5. 现有相册、内置 LUT 和旧 `.rlook` v1/v2 行为不回归。

这是第一版可持续使用的跨相机预设产品。P3 的静态 XMP 和更多 DCP 随后分批加入，不以增加文件数量代替验收。

## 外部条件与范围边界

- 需要可访问的源预设和来源软件参考。没有实际 FL2/FL3 文件时，不以已有 FL 改名充当新风格。
- 受控跨相机准确性验证需要相同场景的配对 RAW；现有不同场景素材仅用于运行和回归。该素材可以由用户提供或另行组织拍摄。

# RawLab 0.9.2

Version `0.9.2`, build `17`. This release extends phone HDR editing to Android
and Windows, adds normal X3F rendering, streamlines presets and batch export,
and improves look browsing. It includes the changes merged after
[0.9.1](https://github.com/dancancer/RawLab/releases/tag/v0.9.1), together with
the fixes below.

## New and improved

- **Phone HDR photos on all four clients.** Android and Windows now import
  supported gain-map JPEG/HEIF photos, keep independent HDR/SDR edits, and offer
  seven basic adjustments, geometry, luminance monitoring, presets, selective
  synchronization and batch export. Export a new gain-map HDR JPEG or an
  explicit SDR result. Switching to SDR editing restores the ordinary look tools.
- **Normal Sigma X3F rendering.** Supported DP1S, Merrill and Quattro photos use
  the shared `normal-v1` CPU renderer across all four clients. Existing edits
  keep their legacy rendering until the user switches modes. Merrill rendering
  also parallelizes expensive processing stages.
- **Presets with fewer steps.** Apply a saved preset directly to the current
  photo, cancel an in-progress check, and undo the completed application. Scope
  summaries show the affected groups, fields and values before adjustments are
  copied, pasted or synchronized.
- **Simpler collection export.** Target checks run automatically; each photo's
  settings are frozen before export. Choose output settings and start with one
  final action. Cancellation, retry and interrupted-task recovery retain
  explicit states and per-photo settings.
- **More photo space and easier look browsing.** Narrow windows and mobile
  landscape layouts leave room for the photo and controls. Filter looks by
  category, search names, return to recently used looks and import from a
  separate action. Unsupported tools explain why they are unavailable.
- **Windows GPU controls.** Supported display-sRGB CUBE looks, including Kodak
  2383-style LUTs, can use Direct3D 11. AI denoising offers automatic or explicit
  hardware GPU selection and a local, redacted diagnostic export.

## Fixes

- Windows display-sRGB CUBE looks no longer unnecessarily fall back to CPU in
  Auto or fail in Force when the Direct3D 11 path supports their contract.
- Windows AI automatic device selection prefers a suitable discrete GPU;
  an explicitly selected unavailable device is reported instead of silently
  switching adapters. Diagnostics retain runtime identity when sessions are reused.
- Android HDR batch preparation treats cancellation as cancellation, preserves
  retryable drafts and distinguishes interrupted tasks. Mixed HDR/SDR batches
  retain each target's editing mode; HDR export avoids a large intermediate Java
  array that could exhaust memory on 12 MP inputs.
- Preset undo clears stale success status, and collection preparation rejects
  stale source, selection or import results before committing a batch.
- Delayed Mac look imports cannot apply to a different photo. Recent looks
  update after successful saving and remove missing library entries.
- Mac and iOS clear incompatible lens-correction settings in the same transaction
  when switching an existing X3F edit from legacy to normal rendering.

## Compatibility and known limits

- HDR processing uses the CPU. Mac HDR editing/export requires **macOS 15+**;
  iOS/iPadOS requires **18+**. Android FP16 HDR presentation requires **API 34+**,
  an HDR-capable display, an available HDR/SDR ratio and a hardware-accelerated
  window. Windows uses FP16/scRGB where supported. Unsupported display conditions
  use SDR presentation; importing and editing are separate from HDR brightness.
- HDR scope remains static gain-map photos. RAW HDR, exposure merging, native
  PQ/HLG and HDR HEIF export are not included. HDR editing offers basic adjustments
  and geometry; LUTs, HSL, curves, color grading and detail/AI effects are available
  through the separate SDR edit rather than applied as HDR operators.
- Normal X3F supports only the documented camera families and adjustment subset.
  DP1S rendering is a measured approximation, and Quattro output differs from
  Sigma Photo Pro. Normal X3F uses CPU; GPU Auto falls back and Force rejects it.
  Additional lens correction and AI denoising are unavailable in normal mode;
  compatible DCP/RLOOK looks use the existing CPU path. On Android
  and Windows, an older legacy-X3F edit with lens correction enabled can be
  rejected when switching to normal mode; disable lens correction before switching.
  See the [X3F rendering contract](../../../lutools/docs/x3f-rendering.md).
- AI denoising still requires hardware Core ML on Apple Silicon or DirectML on
  Windows; there is no CPU neural-inference fallback. Intel Mac, iOS and Android
  packages do not include AI. DualDn and Restormer retain their separate
  noncommercial model licenses.
- Desktop signing, automatic-update and downgrade limits from
  [0.9.0](v0.9.0.md#upgrade-and-compatibility) continue to apply. Mac packages use
  the fixed self-signed certificate and Sparkle EdDSA without notarization.
  Windows uses a signed update descriptor without Authenticode; automatic
  installation requires the current-user Setup, while ZIPs update manually.
  The unsigned IPA requires valid user signing and provisioning.
- The release PR and build provenance distinguish executed UI/runtime checks
  from simulator, VM and automated results. Minimum-OS hardware, physical HDR
  brightness, GPU and mobile-device coverage remain limited to the devices
  actually recorded there; compilation is not device acceptance.

## Verification and source

The release PR and `BUILD-PROVENANCE.json` bind platform packages to their exact
source revisions, full release CI, signature checks and runtime acceptance.
`SHA256SUMS.txt` records the distributed files. The source archive contains the
tagged project sources; dependency versions, source locations, hashes and build
instructions remain in the repository. Private signing material, model weights
and personal RAW samples are excluded from the source archive.

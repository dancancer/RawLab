# 富士 LUT 跨品牌 RAW 应用审查

## 结论

当前实现确实使用 LibRaw 做相机输入转换，再转换到 F-Gamut、进行 F-Log2 编码并应用真实 3D LUT，不是仅凭调色参数模仿富士。但目前只能认定主要流程已接通，不能认定端到端色彩契约已经正确：场景线性输入的标定和高光保留、强度混合、移动端曝光位置及部分输出路径存在具体问题。

## Must-fix

### F1 [P1] 默认 RAW 路径没有建立稳定的场景线性输入标定，并在 LUT 前限制了色域和高光范围

- 位置：`lutools/src/core/raw_processor.cpp:54-71,98-123`；`lutools/src/core/color_converter.cpp:475-505`。
- 触发：默认 CLI/FFI 的 RAW + LUT 路径。CLI 在 `main.cpp:240-244` 选择线性 Adobe RGB；FFI 在 `sony2fuji_c.cpp:817-821` 做同样选择。
- 事实：`gamm={1,1}` 关闭非线性 gamma，但 `no_auto_bright=0` 仍启用逐图直方图自动亮度。随后取得的是 16-bit bitmap，除以 65535 后只有 `[0,1]`。它不是保留完整高光范围、已标定到参考反射率的浮点场景线性缓冲。
- 依赖证据：仓内 LibRaw 0.21.5 的 `src/postprocessing/mem_image.cpp:177-194` 根据 histogram 计算白点并建立输出曲线；`src/postprocessing/postprocessing_utils.cpp:99-117` 将目标 RGB 矩阵结果逐通道 CLIP 到 16-bit 范围。Adobe RGB 外的色彩和超出该中间范围的值无法在后续宽色域转换中恢复。
- 数值证据：官方 F-Log2 将线性 `1,2,4` 分别编码为 `0.568219,0.641440,0.714968`，并不要求输入线性值最多为 1。当前 clamp-only 函数将三者全变为 `0.568219`。默认 RAW 数据的主要范围损失更早发生在 LibRaw bitmap 阶段，不能把 `/65535` 说成产生了大于 1 的数据，也不能声称所有照片都会在后面的 clamp 再次损失大量高光。
- 后果：同一场景值的 LUT 输入曝光依赖画面直方图，LUT 的高光部分无法得到正确的场景曝光范围；饱和色也可能已在较窄中间色域被裁切。
- 最小可信修复：把自动曝光明确做成独立、可关闭的步骤；定义参考灰/曝光尺度和 RAW 白点处理；在裁切前保留足够范围，并在线性域完成曝光与色域处理。仅把 `no_auto_bright` 改为 1 或仅去掉最后 clamp，都不足以独立完成修复。
- 置信度：高，关于实际样片损失比例尚未测量。

### F2 [P1] LUT 强度混合的是 F-Log2 输入和 LUT 输出

- 位置：`lutools/src/ffi/sony2fuji_c.cpp:777-787,1075-1087`。
- 调用链：`convertToFGamut -> applyFLog2Encoding -> applyLUTWithStrength`；后者把 F-Log2 帧保存为 base，然后与胶片模拟 LUT 输出 lerp。
- 触发：RAW 或 buffer 输入，`0 < lut_strength < 1`；RawLab 实际开放该滑块，`Sony2FujiProcessor.swift:104-105,142-143`。
- 后果：混合双方的原色/编码语义不同，不是正确的风格强度；强度 0 和接近 0 的结果甚至不连续。
- 数值证据：内置 PROVIA 将 F-Log2 黑位 `0.092864` 映射到 0；强度 0.01 时错误混合得到约 `23.44/255`，而正常零强度黑位为 0。
- 修复：从相同线性输入生成中性显示结果和风格结果，在明确定义的同一输出空间混合。临时方案可以只支持 0/1。不能用仍输出 F-Log2 的 Log-to-Log709 LUT 充当显示空间中性基底。
- 置信度：高。

### F3 [P1] PNG 导出将 16-bit 缓冲交给 8-bit 编码器，实际改变像素颜色

- 位置：`lutools/src/core/raw_processor.cpp:306-325`；`lutools/src/core/stb_image_write.h:1133-1200`。
- 触发：CLI 输出 `.png`，或 C API 的 `SONY2FUJI_TARGET_FILE + SONY2FUJI_OUTPUT_PNG`，后者在 `sony2fuji_c.cpp:915-939` 调用同一编码器。
- 事实：前者构造 `vector<uint16_t>`，后者每像素消费三个字节，且 PNG IHDR 位深固定为 8。增加 stride 不会把 stb 切到 16-bit。
- 数值证据：纯红 16-bit RGB `[65535,0,0]` 的字节是 `FF FF 00 00 00 00`；写入器读取前三字节，得到黄色 `[255,255,0]`。
- 修复：使用真实 16-bit PNG 编码器，或明确降为 8-bit 并先正确生成 `uint8_t` 缓冲。RawLab 当前使用 ImageIO 导出 JPEG，不受此 PNG 分支影响。
- 置信度：高，已核对实现和字节布局，未生成实际 PNG。

### F4 [P1] 公开 RAW 8-bit 输出选项会按 16-bit 读取并越界

- 位置：`lutools/include/sony2fuji/raw_processor.h:22`；`lutools/src/core/raw_processor.cpp:110-122`。
- 触发：直接使用 C++ API，设置 `outputBitsPerSample=8`。当前 CLI/FFI 默认 16-bit，不触发此问题。
- 事实：LibRaw 按 8-bit 分配/输出三个字节每像素，本项目始终将数据转换为 `uint16_t*`，每像素读取六个字节。
- 后果：颜色错位、错误归一化，并在后半张图读取分配区之外的内存。
- 修复：依据返回的 `image->bits` 分支读取，验证支持的位深，补齐 8/16-bit 测试。
- 置信度：高，静态长度和读取步长证明；未运行 ASan。

## Should-fix

### F5 [P2] 移动端曝光和色温是 LUT 后调色，不是 RAW/LUT 前调整

- 位置：`lutools/src/ffi/sony2fuji_c.cpp:815-816,1063-1098,467-501`；`RawLab/RawLab/Core/RawProcessing/Sony2FujiProcessor+Helpers.swift:55-67`。
- 触发：RawLab 调整曝光、色温/色调。RAW 解码阶段曝光和亮度固定为 0 EV/1；曝光倍数及温度 RGB 乘数在 LUT 之后应用。
- 后果：不能用曝光滑块正确定位胶片 LUT 的输入曝光，不能用 LUT 后色温代替 RAW 白平衡；CLI 的 `--exposure` 则在 LibRaw 处理前生效，两条路径语义不同。
- 数值证据：用同一中性线性输入 0.18、内置 PROVIA 和单位白平衡，R 通道 LUT 输出约 0.457785。LUT 后 +1 EV 为 0.915571；正确先将线性输入倍增至 0.36 再过 LUT，为 0.634892。此为隔离曝光步骤的数值比较，不是完整 App 截图测量。
- 修复：区分输入曝光/白平衡与输出调色，把前者移至正确的线性/RAW 阶段。避免将所有现有对比度等输出调色无差别搬到 LUT 前。
- 置信度：高。

### F6 [P2] 保留 F-Log2 曲线的 LUT 被作为最终照片显示和导出

- 位置：`RawLab/RawLab/Core/ViewModel/RawEditorViewModel+LUT.swift:63-78`；`RawLab/RawLab/Core/RawProcessing/Sony2FujiProcessor+Helpers.swift:150-175`；`lutools/src/ffi/sony2fuji_c.cpp:1080-1090`。
- 触发：选择已打包的 `X100VI_FLog2_FGamut_to_FLog2_BT.709_33grid_V.1.00.cube`。其头部第 3 行明确是 `F-Log2 to F-Log2`；新 65-grid 的 FLog2-709 同样如此。
- 后果：LUT 只转换色域而保留 Log 曲线，输出却直接作为 sRGB CGImage/JPEG，呈现低反差的 Log 图，而不是完成显示转换的照片。
- 修复：区分 LUT 输入/输出原色、传递曲线和用途；隐藏纯技术中间转换 LUT，或补后续显示变换。外部 F-Log2 C、sRGB LUT 也不能因为扩展名相同而进入固定 F-Gamut/F-Log2 路径。
- 置信度：高。不能从其他胶片 LUT 的 BT.709 原色声明单独推断其完整输出传递曲线；本报告没有武断认定所有胶片 LUT 都存在同一种 gamma 错误。

### F7 [P2] 自定义 CUBE 的域、输出范围和轴顺序处理不符合格式契约

- 位置：`lutools/src/core/lut_parser.cpp:50-66,146-176,198-203`；`lutools/src/core/lut_applicator.cpp:23-29,83-86`。
- 触发：CLI/C API 加载非默认 domain、超范围输出或通道重映射的合法 3D CUBE。文档 `lutools/docs/usage-guide.md:233-234` 声称任何 3D CUBE 均可使用。
- 事实：DOMAIN_MIN/MAX 未保存；表值被提前 clamp；文件轴顺序通过输出通道变化量猜测。CUBE 的标准顺序实际为 R-fast，输出通道变化并不能证明输入轴顺序。
- 反例一：domain `[0.25,0.75]` 的表，输入 0.375 应查归一化坐标 0.25，当前查 0.375。
- 反例二：标准 R-fast、size 2 的红蓝交换表，首段蓝输出变化最大，被误判为 B-fast；输入红 `(1,0,0)` 得到红而不是应有的蓝 `(0,0,1)`。
- 修复：遵循格式固定顺序，保存并应用 domain，保留浮点表值直到明确的输出边界；不支持的契约显式拒绝。当前 16 个内置 Fuji LUT 均为 `[0,1]` 数据并被探测为 R-fast，本项没有证明它们已被读错。
- 置信度：高。

### F8 [P2] 公共示例绕过真实相机校正并漏掉 F-Log2 编码

- 位置：`lutools/examples/simple_example.cpp:30-37,47-80`；`lutools/src/core/color_converter.cpp:188-198`。
- 触发：按 C++ 示例集成。默认 options 未启用 Adobe/ACES，因此 LibRaw 输出 `output_color=0` 的 raw-color/native 数据；随后使用类似 sRGB 的占位 Sony 矩阵，直接进入 F-Log2 LUT。
- 后果：这里既没有正确的该机型输入变换，也没有 F-Log2 编码，不能产生与 CLI 相同的结果；它不是默认 CLI 错误的证据，而是公开示例自身错误。
- 修复：示例复用已定义的完整处理管线，避免再维护一个错误的 native 转换捷径；同步修正文档中的旧矩阵与漏步骤示例。
- 置信度：高。

### F9 [P2] Metal no-copy 缓冲未满足页对齐合同

- 位置：`lutools/src/gpu/metal_lut.mm:98-106`；`lutools/src/gpu/lut_gpu.cpp:87-96`。
- 触发：iOS 库使用 GPU Auto/Force，输入 `vector<RGB>` 的起始地址或 `pixels.size()*sizeof(RGB)` 不满足 Metal 的页对齐要求。小尺寸图的字节长度尤其不满足该约束。
- 后果：缓冲创建可能失败或触发 API 校验；Auto 在失败返回 false 时回退 CPU，Force 返回处理错误，不能保证启用 GPU 就可执行。
- 修复：用 Metal 自己分配的 buffer 并复制，或采用符合要求的页对齐分配与向上对齐长度，保留逻辑 pixel_count。
- 边界：`Sony2FujiProcessor+Helpers.swift:40-45` 明确设置 GPU_OFF，因此不是当前 RawLab 默认成像错误。GPU 设备运行验证 NOT REACHED。
- 置信度：高，基于 API 合同和分配方式；不声称已观测设备崩溃。

### F10 [P2] 现有测试不能验证色彩链路正确性

- 位置：`lutools/build.sh:173-190`；`lutools/test.sh:12-78`。
- 事实：build.sh 的测试主体仍是 TODO；test.sh 检查可执行文件、帮助和资源存在，不断言任何图像/色彩结果。build.sh 还查找 `build/sony2fuji_cli`，而 CMake 的 OUTPUT_NAME 是 `sony2fuji`。
- 应补的最小回归：F-Log2 的 0/18%/90% 锚点、色域原色/白点、已知曝光尺度的高光阶梯、强度 0/近零/0.5/1、输入曝光位置、CUBE domain/红蓝交换、PNG 位深/颜色回读、RAW 8/16-bit、CPU/GPU 同输入一致性。
- 跨品牌验收另需受控光源、灰卡/色卡与曝光阶梯样片；只打开一张 ARW 或 DJI DNG 不能证明色彩还原准确。
- 置信度：高。

## 已确认正确及未采纳的指控

- `color_converter.cpp:200-207` 的 F-Gamut 矩阵对应官方原色，F-Log2 常数与官方数据表一致。独立计算得到 10-bit 码值：0 -> 94.999872，0.18 -> 400.000408，0.9 -> 569.946408，与官方约 95/400/570 一致。
- 默认 CLI/FFI 使用 LibRaw 的 Adobe RGB 输出，不走 `getSonyNativeToXYZ()` 占位矩阵；不能把示例缺陷误判为默认主链路的相机校正缺失。
- CPU 三线性插值的八顶点逻辑成立。GPU texture 数据轴布局和半纹素坐标与 CPU 逻辑相符；没有发现内置 LUT 的红蓝颠倒证据，设备精度一致性未运行。
- ACES 的 softplus/percentile 归一化是额外的图像自适应处理，不应被描述为透明编码变换。没有将该可选模式当成已证明解决 F1 的替代方案。
- 其他胶片模拟 LUT 的 BT.709 声明首先是色域信息；仍需明确其输出显示假设、范围和最终 ICC/编码约定，不能凭名字断言其传递曲线必然等于 sRGB 或 BT.709 OETF。

## 与原对话的核对

- “RAW -> 线性 Adobe RGB -> F-Gamut -> F-Log2 -> 3D LUT”的默认调用顺序成立。
- 原对话指出的强度混合问题确认，而且存在零强度附近的不连续。
- 自动亮度和范围限制不仅是一般风格差异，还阻碍稳定输入标定；但必须区分 LibRaw 早期裁切与后续 clamp 的实际可达范围。
- 新 LUT 文件夹确实含 10 种胶片模拟和 2 种技术转换。RawLab 当前打包的是旧 X100VI 四个 LUT，不能把仓库存在新文件等同于 App 已提供全部十种风格。
- “正确跨品牌应用”与“复刻富士机内 JPEG”仍是两项不同验收：前者应先通过数值契约测试，后者还需要机型/光源标定、实拍比较及机内局部处理差异研究。

## 建议顺序

1. 先定义并验证输入线性值、曝光尺度与高光策略，然后统一 CLI/FFI 管线。
2. 修正强度混合及输入曝光/白平衡位置，明确 LUT 输入输出契约。
3. 修复 PNG/8-bit 内存读取等确定性错误及公开示例。
4. 建立数值回归与跨品牌样片验收，再做性能优化。

可选性能优化：RawLab 每次 RAW 预览都重新解码整张图，缩小尺寸在后端处理末尾才发生。可缓存带明确色彩状态的解码线性缓冲，按 RAW/白平衡等输入参数失效，从缓存重新计算 LUT 和显示结果；先保证状态和数值正确，再启用 GPU。四面体插值可以作为与参考软件一致性的进一步比较项，不是本次最先要修的内容。
